Manual avançado do mercadopagopix

Biblioteca Go, sem dependências, para criar e acompanhar pagamentos PIX pela API do Mercado Pago. Este manual vai além do README: configuração fina, idempotência, marketplace, paginação, resiliência, webhooks em produção e o comportamento real do sandbox.

v1.1.0 Go 1.23+ Só biblioteca padrão 35 testes unitários · 87,5% de cobertura 15 testes de integração no sandbox

1. Visão geral

Um Client imutável e seguro para uso concorrente encapsula token, cabeçalhos fixos, timeout e a política de retry. Todos os métodos recebem context.Context e aceitam opções por chamada no fim.

go
import mp "github.com/reinanbr/mercadopago-sdk-go" // pacote mercadopagopix

client, err := mp.NewFromEnv(
    mp.WithIntegratorID("dev_123"),
    mp.WithTimeout(20 * time.Second),
)
if err != nil {
    log.Fatal(err) // mp.ErrMissingToken se nenhuma variável estiver definida
}

p, err := client.CreatePix(ctx, mp.CreatePixRequest{
    Amount:            mp.Reais(49.90),
    Description:       "Pedido #1042",
    Payer:             mp.Payer{Email: "cliente@example.com"},
    ExternalReference: "pedido-1042",
    ExpiresIn:         30 * time.Minute,
}, mp.WithIdempotencyKey("pedido-1042"))

Arquivos da lib

  • client.go: cliente, opções, retry, Do
  • pix.go: criar, consultar, cancelar, estornar, aguardar
  • search.go: busca e iterador de paginação
  • webhook.go: validador de assinatura e handler HTTP
  • payment.go, amount.go, errors.go, env.go

Ferramentas

  • make test: testes unitários
  • make test-integration: testes no sandbox real
  • make report: relatórios em reports/*.md
  • examples/create, examples/webhook

2. Configurando o cliente

Credenciais

New(token) recebe o token direto. NewFromEnv() procura, em ordem, MERCADOPAGO_ACCESS_TOKEN, ACCESS_TOKEN e TOKEN. Para ler um arquivo .env sem dependências externas:

go
// Carrega o .env no ambiente sem sobrescrever variáveis já definidas.
_ = mp.LoadEnvFile(".env")

// Ou só leia os valores, sem tocar no ambiente do processo
// (útil quando o arquivo tem chaves como USER, que colidem com o shell).
vars, err := mp.ReadEnvFile(".env.test")
client, err := mp.New(vars["ACCESS_TOKEN"])

client.TestMode()        // true para tokens "TEST-"
acc, err := client.Me(ctx) // conta dona do token: ID, Nickname, SiteID, Tags
acc.IsTestUser()         // a conta é um usuário de teste do MP?
Produção x teste

Tokens APP_USR- movimentam dinheiro de verdade. Use client.TestMode() como trava em scripts e testes; os testes de integração desta lib se recusam a rodar com token de produção, a menos que MP_ALLOW_LIVE=1.

Ordem importa

WithTimeout copia o http.Client atual e muda o timeout. Coloque-o depois de WithHTTPClient, senão o seu client substitui o timeout.

3. Opções por chamada

Todo método aceita ...CallOption no fim. Elas valem só para aquela chamada e para todas as suas tentativas de retry.

OpçãoEfeito
WithIdempotencyKey(k)Define o X-Idempotency-Key (1 a 64 caracteres). Repetir a chave devolve o resultado da primeira requisição, sem nova cobrança ou estorno.
WithAccessToken(t)Usa outro token nesta chamada, por exemplo o token OAuth de um vendedor em um marketplace.
WithCallHeader(k, v)Cabeçalho extra só nesta chamada (sobrepõe o WithHeader do cliente).

Marketplace: um cliente, muitos vendedores

go
// Um único Client (com retry, timeout e headers) atende todos os vendedores.
func cobrar(ctx context.Context, seller Seller, pedido Pedido) (*mp.Payment, error) {
    return client.CreatePix(ctx, mp.CreatePixRequest{
        Amount:            pedido.Total,
        Payer:             mp.Payer{Email: pedido.Email},
        ExternalReference: pedido.ID,
    },
        mp.WithAccessToken(seller.OAuthToken),  // cobrança cai na conta do vendedor
        mp.WithIdempotencyKey("pix-"+pedido.ID),
    )
}

Precedência da chave de idempotência

WithIdempotencyKey›CreatePixRequest.IdempotencyKey›UUID aleatório

Requisições POST sempre levam uma chave. GET e PUT só levam se você passar uma.

4. Valores (Amount)

Amount é um int64 em centavos. Nada de float64 acumulando erro de arredondamento.

go
a := mp.Reais(0.1 + 0.2) // 30 centavos (arredonda para o centavo mais próximo)
b := mp.Cents(4990)      // R$ 49,90
total := a + b           // soma inteira, exata

total.String()   // "R$ 50,20"   (formato brasileiro, com milhar: "R$ 1.234,56")
total.Cents()    // 5020
total.Float64()  // 50.2
json.Marshal(b)  // 49.90       (como a API espera)

Na leitura, Amount aceita número, string numérica e null.

Usando o resultado

go
p.QRCode              // PIX "copia e cola" (EMV, começa com 000201...)

p.TicketURL           // página do MP com o QR (no sandbox: .../sandbox/payments/...)

    w.Header().Set("Content-Type", "image/png")
    w.Write(png)
})
Idempotência por pedido

Use o ID do pedido como chave (WithIdempotencyKey("pix-"+pedido.ID)). Se o processo cair depois de enviar e antes de salvar a resposta, a próxima tentativa devolve o mesmo PIX em vez de gerar outro. Isso foi confirmado no sandbox pelo teste TestIntegrationIdempotency.

Aguardando o pagamento (polling)

go
ctx, cancel := context.WithTimeout(ctx, 10*time.Minute)
defer cancel()

p, err := client.WaitForPayment(ctx, id, 5*time.Second)
switch {
case errors.Is(err, mp.ErrExpired):
    // ainda pending após DateOfExpiration
case errors.Is(err, context.DeadlineExceeded):
    // p é o último estado conhecido (pode ser nil se nenhuma consulta deu certo)
case err != nil:
    // erro de API ou de rede
case p.IsPaid():
    // aprovado
}
Polling x webhook

Use WaitForPayment em CLIs, testes e telas de checkout curtas. Em produção, use webhooks e, se quiser, polling como reforço.

7. Cancelamento, atualização e estornos

go
p, err := client.CancelPayment(ctx, id)             // pending → cancelled (detail: by_collector)

r, err := client.Refund(ctx, id, 0)                  // estorno total
r, err := client.Refund(ctx, id, mp.Reais(10),       // estorno parcial
    mp.WithIdempotencyKey("refund-"+pedido.ID+"-1"))
rs, err := client.ListRefunds(ctx, id)
r, err := client.GetRefund(ctx, id, refundID)
Restrições observadas no sandbox

• Estornar um PIX pendente falha com 400 (causa 120010: "Transaction Intent must be in processed state").

• Listar estornos de um PIX pendente retorna 403 ("At least one policy returned UNAUTHORIZED").

• UpdatePayment só serve, na prática, para cancelar: metadata (403), external_reference (401) e date_of_expiration (400, causa 4243) são recusados.

Todas as páginas, com iterador (Go 1.23)

go
var total mp.Amount
for p, err := range client.AllPayments(ctx, mp.SearchParams{Status: mp.StatusApproved, Limit: 100}) {
    if err != nil {
        return err // o erro é entregue uma vez e a iteração termina
    }
    total += p.Amount
    if total > mp.Reais(10_000) {
        break // parar cedo não busca mais páginas
    }
}

As páginas só são buscadas sob demanda. A iteração para quando uma página vem vazia ou quando o offset alcança paging.total.

Peculiaridades do sandbox

No sandbox, só external_reference (sozinho ou com status) encontrou pagamentos, e apenas enquanto um único pagamento usava aquela referência. payment_method_id, intervalos de data e a busca sem filtros devolveram 0 resultados. Em produção a busca é completa; nos testes, use referências únicas.

9. Retry e resiliência

go
mp.DefaultRetryPolicy() // = RetryPolicy{
//     MaxRetries:   3,
//     InitialDelay: 500 * time.Millisecond, // dobra a cada tentativa
//     MaxDelay:     30 * time.Second,       // teto para cada espera (inclui Retry-After)
//     Jitter:       true,                   // espera entre 50% e 100% do valor
//     RetryOn:      []int{429, 500, 502, 503, 504},
// }
  • O que é repetido: erros de rede e os status listados em RetryOn. Erros 4xx de validação nunca são repetidos.
  • Retry-After: quando a API envia (segundos ou data HTTP), a espera respeita o valor, limitado por MaxDelay.
  • Segurança: todas as tentativas de uma chamada usam a mesma chave de idempotência, então um POST repetido nunca cobra duas vezes.
  • Contexto: cancelar o ctx interrompe também a espera entre tentativas.

Métricas e logs com OnRetry

go
policy := mp.DefaultRetryPolicy()
policy.OnRetry = func(i mp.RetryInfo) {
    slog.Warn("mercadopago retry",
        "method", i.Method, "path", i.Path,
        "attempt", i.Attempt, "delay", i.Delay, "err", i.Err)
    retryCounter.WithLabelValues(i.Path).Inc()
}
client, _ := mp.New(token, mp.WithRetryPolicy(policy))

// Sem retry (por exemplo, em um job que já tem a própria fila de retentativas):
client, _ = mp.New(token, mp.WithRetries(0, 0))

11. Webhooks

O handler valida a assinatura, busca o pagamento na API (o corpo do webhook nunca é usado como fonte de verdade) e só então chama o seu código.

POST do MP→valida x-signature→200 (async)→GetPayment→seu Handle

Configuração de produção

go
http.Handle("/webhooks/mercadopago", client.NewWebhookHandler(mp.WebhookConfig{
    Validator: &mp.WebhookValidator{
        Secret:    os.Getenv("MERCADOPAGO_WEBHOOK_SECRET"),
        Tolerance: 10 * time.Minute, // proteção contra replay
    },
    Async:   true,            // responde 200 na hora; MP exige resposta em 22s
    Timeout: 2 * time.Minute, // limite para GetPayment + Handle
    Handle: func(ctx context.Context, p *mp.Payment) error {
        return pedidos.MarcarStatus(ctx, p.ExternalReference, p.Status, p.ID) // idempotente!
    },
    OnError: func(n *mp.Notification, err error) {
        slog.Error("webhook", "request_id", n.RequestID, "err", err)
    },
}))

Modo síncrono (padrão)

  • 401: assinatura inválida
  • 200: evento que não é de pagamento (ignorado)
  • 502: falha ao buscar o pagamento
  • 500: seu Handle retornou erro, e o MP reenvia

Modo assíncrono

  • 200 assim que a assinatura é validada
  • Processamento em goroutine com Timeout
  • Erros vão para OnError; não há reenvio automático do MP
  • Use quando o Handle pode demorar
Entregas repetidas

Se não receber resposta em 22 segundos, o Mercado Pago reenvia a cada 15 minutos, e pode mandar o mesmo evento mais de uma vez mesmo quando você responde. O seu Handle precisa ser idempotente, por exemplo com um UPDATE ... WHERE status <> 'approved' ou uma tabela de eventos já processados.

Como a assinatura é calculada

O cabeçalho x-signature tem o formato ts=1700000000,v1=<hex>. O manifesto assinado com HMAC-SHA256 e a chave secreta da aplicação é:

text
id:<data.id da query>;request-id:<x-request-id>;ts:<ts>;
  • Partes ausentes (sem data.id ou sem x-request-id) são omitidas do manifesto.
  • O data.id é comparado como recebido e, se tiver letras maiúsculas, também em minúsculas. O SDK oficial usa o valor como recebido, enquanto a documentação pede minúsculas; aceitamos os dois.
  • O hash em hexadecimal é comparado sem diferenciar maiúsculas e em tempo constante (hmac.Equal).
  • Versions permite aceitar versões futuras (v2…) por ordem de preferência.
  • Notificações de QR code presencial (Point) não são assinadas pelo MP.

Motivos de rejeição

SignatureFailureCausa
SignatureMissingHeaderSem x-signature.
SignatureMalformedHeaderFormato inválido ou ts não numérico.
SignatureMissingTSHash presente, sem ts.
SignatureMissingHashNenhuma das Versions aceitas está no cabeçalho.
SignatureMismatchHMAC não confere (secret errado ou dados adulterados).
SignatureOutOfTolerancets fora da janela de Tolerance.

Uso manual (frameworks como Gin, Echo, Fiber)

go
v := mp.WebhookValidator{Secret: secret, Tolerance: 10 * time.Minute}
err := v.Validate(c.GetHeader("X-Signature"), c.GetHeader("X-Request-Id"), c.Query("data.id"))

var se *mp.SignatureError
if errors.As(err, &se) {
    slog.Warn("assinatura inválida", "reason", se.Reason, "request_id", se.RequestID)
    c.Status(401) // não devolva o motivo no corpo
    return
}

// Ou leia a notificação inteira (inclui IPN legado ?topic=payment&id=123):
n, err := mp.ParseWebhook(r, secret)
id, err := n.PaymentID()

12. Chamadas cruas (Do)

Para endpoints que a lib não cobre, Do reaproveita autenticação, cabeçalhos, retry, idempotência e erros tipados.

go
var tipos []struct {
    ID   string `json:"id"`
    Name string `json:"name"`
}
err := client.Do(ctx, http.MethodGet, "/v1/identification_types", nil, nil, &tipos)
// no sandbox: [CPF CNPJ]

var merchantOrder map[string]any
err = client.Do(ctx, http.MethodGet, "/merchant_orders/123", nil, nil, &merchantOrder)

// POST sempre leva X-Idempotency-Key (aleatória ou WithIdempotencyKey):
err = client.Do(ctx, http.MethodPost, "/v1/algum-recurso", nil, body, &out,
    mp.WithIdempotencyKey("op-42"))

Respostas vazias (204) não são decodificadas e não geram erro.

13. Receitas

Checkout completo, com tolerância a falhas

go
func (s *Service) Checkout(ctx context.Context, pedido Pedido) (*mp.Payment, error) {
    // 1. Reaproveita um PIX pendente e ainda válido.
    if pedido.PaymentID != 0 {
        if p, err := s.mp.GetPayment(ctx, pedido.PaymentID); err == nil &&
            p.Status == mp.StatusPending && p.TimeToExpiration() > 2*time.Minute {
            return p, nil
        }
    }
    // 2. Cria com chave determinística: repetir esta função não duplica a cobrança.
    tentativa := pedido.Tentativas + 1
    p, err := s.mp.CreatePix(ctx, mp.CreatePixRequest{
        Amount:            pedido.Total,
        Description:       "Pedido " + pedido.ID,
        Payer:             mp.Payer{Email: pedido.Email},
        ExternalReference: pedido.ID,
        NotificationURL:   s.webhookURL,
        ExpiresIn:         30 * time.Minute,
        Metadata:          map[string]any{"tentativa": tentativa},
    }, mp.WithIdempotencyKey(fmt.Sprintf("pix-%s-%d", pedido.ID, tentativa)))
    if err != nil {
        return nil, err
    }
    // 3. Persiste o vínculo antes de devolver o QR ao cliente.
    return p, s.db.SalvarPagamento(ctx, pedido.ID, p.ID, tentativa)
}

15. Comparação com o SDK oficial (sdk-python)

O sdk-python foi estudado por engenharia reversa (v3.6.0). Trouxemos o que ele faz bem e corrigimos o que ele deixa a desejar.

O que não copiamos

O SDK envia x-product-id e x-tracking-id com identificadores próprios do SDK oficial. Não reproduzimos esses valores para não nos passarmos por ele; use WithUserAgent e WithPlatformID para se identificar.
